# GitHub Issue Generator

작업 내용을 받아 팀 컨벤션에 맞춘 이슈를 작성하고, 사용자 승인을 받은 뒤 `gh`로 GitHub에 생성한다.

## 절대 규칙

- **이슈 생성 전에 무조건 사용자 검수를 받는다.** 제목, 라벨, 본문을 먼저 제시하고, 사용자가 "올려줘", "생성해", "진행해" 같이 명시적으로 승인할 때만 `gh issue create`를 실행한다. 이슈는 한번 만들면 팀 전체에 보이고 되돌리려면 닫거나 지워야 한다. `/issue`만 호출했을 때도 이 절차를 거친다.
- 모든 텍스트는 한국어로 작성한다.
- 제목 형식은 `[CATEGORY] 설명`이다. 대괄호와 그 뒤의 공백을 지킨다.
- 본문은 카테고리와 무관하게 공통 템플릿 하나를 쓴다. BUG만 재현 절차 섹션을 하나 더 둔다. 그 밖의 어떤 카테고리도 섹션을 늘리거나 줄이지 않는다.
- 본문 문장은 "-습니다" 완결형으로 쓴다. 체크리스트 항목은 명사형으로 끝내도 된다.
- 섹션 헤더는 공통 템플릿의 세 개와 BUG의 재현 절차를 이모지까지 글자 그대로 쓴다. 카테고리에 맞춰 헤더 이름을 바꾸지 않는다.
- 진행 체크리스트에는 **테스트 항목과 문서 갱신 항목을 각각 한 줄 이상 둔다.** 해당 작업이 없으면 그 자리에 없는 이유를 적는다. 두 줄을 비워두거나 지우지 않는다.
- 아직 하지 않은 일을 한 것처럼 쓰지 않는다. **앞으로 할 일은 "~합니다"로 쓴다.** 반대로 이미 관찰했거나 끝난 사실은 과거형으로 쓰고 근거를 함께 적는다 — 버그를 확인한 환경과 실제 결과, 선행 이슈나 PR에서 끝난 작업이 그렇다. 끝난 작업은 어느 이슈나 PR에서 끝났는지 번호를 붙여 계획과 구분한다.

## CATEGORY와 라벨

| CATEGORY | 라벨 | 용도 |
|---|---|---|
| FEATURE | `✨ feature` | 새 기능, 기존 기능 변경 |
| BUG | `🐞 bug` | 버그 |
| REFACTOR | `♻️ refactor` | 동작 변화 없는 코드 변경 |
| CHORE | `⚙️ chore` | 빌드, 설정, 의존성, 인프라 |
| TEST | `✅ test` | 테스트 작성이나 수정 |
| DOCS | `📝 docs` | 문서 |

**라벨명은 이모지가 이름의 일부다.** `--label feature`는 없는 라벨이라 실패한다. `--label "✨ feature"`처럼 이모지를 포함해 따옴표로 감싼다. 라벨은 하나만 붙인다.

브랜치 라벨과 커밋 타입으로의 매핑은 `/branch` SKILL.md의 표가 단일 소스다. 이 표를 여기서 다시 정의하지 않는다.

## 본문 템플릿

```markdown
### 📄 작업 설명
{1~3문장. 무엇을 왜 하는지. 버그라면 현상과 기대 동작의 차이, 확인한 환경까지 여기에 씁니다}

### 📈 진행 체크리스트
- [ ] {구현 항목}
- [ ] {구현 항목}
- [ ] {테스트 항목. 없으면 "테스트 추가 없음: 이유"}
- [ ] {문서 갱신 항목. 없으면 "문서 갱신 없음: 이유"}

### 👍🏻 추가 정보
{관련 이슈나 PR 번호, 참고할 코드나 문서 위치. 없으면 _No response_}
```

### BUG 전용 섹션

BUG는 작업 설명과 진행 체크리스트 **사이**에 재현 절차를 끼운다.

```markdown
### 📈 재현 절차
1. {단계}
2. {단계}
3. 기대 결과와 실제 결과
```

### 템플릿 우회

`gh issue create`에 `--title`과 `--body`를 주면 카테고리별 이슈 템플릿을 거치지 않으므로 이 공통 형식이 그대로 올라간다. 웹 UI로 만들면 템플릿을 고르게 되고, 카테고리마다 필드 이름과 구성이 달라 공통 형식이 깨진다. 체크리스트 칸이 없는 카테고리에서는 테스트 항목과 문서 갱신 항목까지 사라진다. 그래서 웹 UI를 쓰지 않는다.

## 문서 갱신 판단

체크리스트의 문서 갱신 항목은 [.agents/rules/docs.md](../../rules/docs.md)의 "변경에 따른 갱신 대상" 표에서 찾는다. 그 표가 단일 소스이며 여기서 재정의하지 않는다. 판단할 때 주의할 점도 그 문서에 있다.

## 테스트 판단

테스트 항목을 넣어야 하는지는 [.agents/rules/test.md](../../rules/test.md)의 "테스트가 반드시 있어야 하는 변경"을 따른다. 기능 추가와 버그 수정은 반드시 있고, 버그 수정은 수정 전에 실패하는 테스트가 들어간다.

## Workflow

1. CATEGORY를 식별한다. 입력에 없으면 묻는다.
2. 템플릿을 채운다. 작업 항목이 없으면 변경 대상을 읽고 추측한다. 테스트 항목과 문서 갱신 항목은 위 두 절의 기준으로 정한다.
3. 제목과 라벨, 본문을 검수 요청으로 제시한다. 추측한 항목이 있으면 밝히고 함께 묻는다.
4. 승인 후 생성하고, 번호와 URL, 남은 수동 작업을 알린다.

## 사용 예시

### FEATURE

입력:

```
/issue FEATURE 열차 조회 잔여좌석을 Redis 단일 소스로. 작업: 계산 교체, DB 집계 제거
```

검수 요청:

```
이슈 생성 전 검수 요청

제목: [FEATURE] 열차 조회 잔여좌석 계산을 Redis 단일 소스로 전환
라벨: ✨ feature

본문:
---
### 📄 작업 설명
열차 조회의 잔여좌석을 DB 집계와 Redis 점유 양쪽에서 계산해 두 값이 어긋날 수 있습니다. 좌석 캐시와 점유 Hash만 읽어 계산하도록 바꿔 단일 소스로 만듭니다.

### 📈 진행 체크리스트
- [ ] 잔여좌석 계산을 좌석 캐시와 점유 Hash 조회로 교체
- [ ] DB 집계 경로 제거
- [ ] 점유가 있는 좌석과 없는 좌석의 잔여석 계산이 맞는지 검증하는 서비스 통합 테스트 추가
- [ ] docs/train-cache-schema.md에 잔여좌석 계산이 읽는 키와 값 타입 추가

### 👍🏻 추가 정보
_No response_
---

이대로 이슈를 생성할까요? 수정이 필요하면 말씀해주세요.
```

입력에는 작업 항목이 두 개였는데 체크리스트는 네 줄이다. 뒤의 두 줄이 테스트 항목과 문서 갱신 항목이다. 좌석 캐시를 읽는 방식이 바뀌므로 문서 갱신 대상은 `docs/train-cache-schema.md`다.

아래 두 예시는 본문만 보인다. 제목과 라벨, 검수 요청을 붙이는 방식은 위와 같다.

### BUG

입력:

```
/issue BUG 예매 삭제 API가 소유자 검증을 안 하고 Redis 좌석 점유도 정리하지 않음
```

본문:

```markdown
### 📄 작업 설명
`DELETE /api/v1/bookings`는 요청 본문의 `bookingId`로 삭제만 호출하므로 요청자가 예매의 주인인지 확인하지 않습니다. 또한 Redis 좌석 점유를 정리하지 않아 결제가 확정된 좌석의 `B:{bookingId}` field가 객차 키 만료까지 남습니다. 본인 예매만 지울 수 있고, 지운 예매의 점유 field가 함께 정리되어야 합니다. #270 첫 번째 PR이 반영된 develop에서 확인했습니다.

### 📈 재현 절차
1. 사용자 A가 좌석을 예약하고 결제합니다.
2. 로그인한 사용자 B가 A의 `bookingId`로 삭제를 요청합니다.
3. 기대 결과는 권한 오류이고, 실제 결과는 A의 예매가 삭제됩니다.
4. 다른 사용자가 같은 좌석을 예약하면 기대 결과는 예약 성공이고, 실제 결과는 좌석 충돌로 거절됩니다.

### 📈 진행 체크리스트
- [ ] 삭제 요청자와 예매 소유자가 같은지 검증 추가
- [ ] DB 삭제를 커밋한 뒤 자기 `B:{bookingId}` 값일 때만 지우는 비교 삭제 호출
- [ ] 다른 사용자의 예매를 지우려는 요청이 거절되는지, 삭제 후 같은 좌석을 다시 예약할 수 있는지 검증하는 테스트 추가
- [ ] docs/reservation-cache-schema.md에 예매 삭제 시 점유 정리 규칙 추가

### 👍🏻 추가 정보
_No response_
```

환경은 작업 설명 마지막 문장에 넣었고, 이미 확인한 사실이므로 과거형으로 썼다. 재현 절차의 기대 결과와 실제 결과를 작업 설명에 중복해서 쓰지 않는다.

### CHORE

입력:

```
/issue CHORE Gradle 빌드 캐시와 병렬 실행으로 빌드 시간 단축
```

본문:

```markdown
### 📄 작업 설명
멀티 모듈 빌드가 매번 전체를 다시 컴파일해 로컬 빌드와 CI가 느립니다. `gradle.properties`를 추가해 빌드 캐시와 병렬 실행을 켜고, 적용 전후 빌드 시간을 비교합니다.

### 📈 진행 체크리스트
- [ ] gradle.properties 추가 (빌드 캐시, 병렬 실행, JVM 힙)
- [ ] clean 빌드와 증분 빌드 시간을 적용 전후로 측정
- [ ] 테스트 추가 없음: 빌드 설정 변경이라 프로덕션 동작이 바뀌지 않고, 기존 테스트가 그대로 통과하는지로 검증합니다
- [ ] 문서 갱신 없음: 빌드 플래그를 다루는 문서가 없습니다

### 👍🏻 추가 정보
_No response_
```

"전체 테스트 통과 확인"은 테스트를 새로 쓰는 일이 아니므로 테스트 항목을 대신하지 못한다.

이 입력에는 작업 항목이 없었으므로 본문 뒤에 추측한 부분을 밝히고 함께 묻는다.

```
위 두 작업 항목은 gradle.properties가 아직 없고 멀티 모듈 빌드라는 점을 보고 추측했습니다.
측정 기준을 CI 빌드 시간까지 넣을지, 힙 설정을 이 이슈에서 함께 다룰지 알려주세요.
```

## 예외 처리

### CATEGORY 미지정

```
CATEGORY를 알려주세요.

사용 가능: FEATURE, BUG, REFACTOR, CHORE, TEST, DOCS

예시: /issue FEATURE 사용자 로그인
```

### 체크리스트 추출 불가

빈 placeholder를 내놓지 않는다. 변경 대상과 이슈 설명으로 추측한 항목을 적어 초안을 완성하고, 본문 뒤에 무엇을 추측했는지와 원하는 것을 함께 묻는다.

```
작업 항목이 입력에 없어 아래 세 항목은 {근거}를 보고 추측했습니다.
- {추측한 항목}
- {추측한 항목}
- {추측한 항목}

더 넣을 항목이나 뺄 항목이 있으면 알려주세요. 쪼개거나 합칠 항목이 있어도 말씀해주세요.
```

추측할 근거조차 없으면 추측하지 않고 무엇을 할 계획인지 먼저 묻는다.

```
작업 항목을 추측할 근거가 없습니다. 어떤 작업으로 나눌 계획인지 알려주세요.
그 사이 작업 설명과 테스트 항목, 문서 갱신 항목은 채워뒀습니다.
```

### 생성 실패

`gh issue create`가 실패하면 본문을 버리지 않는다. 같은 본문을 그대로 두고 원인만 처리한다.

| 오류 | 원인 | 처리 |
|---|---|---|
| `could not add label` | 라벨명에 이모지를 빼먹었다 | `gh label list`로 정확한 이름을 확인해 다시 실행한다 |
| `authentication required` | 로그인이 끊겼다 | 사용자에게 `gh auth login` 실행을 요청한다 |
| `missing required scopes` | `--project`를 썼는데 스코프가 없다 | `--project` 없이 생성하고 프로젝트 추가를 안내한다 |

### 문서 갱신 대상 불명

표에 해당하지 않고 코드를 읽어도 영향 문서가 분명하지 않으면, 체크리스트에 추측한 문서명을 넣지 않는다. 대신 사용자에게 묻는다.

```
이 변경이 어떤 문서를 무효화하는지 판단하지 못했습니다.
갱신할 문서가 없다면 "문서 갱신 없음: 해당 없음"으로 두겠습니다.
```
