# Pull Request

현재 브랜치의 작업을 팀 템플릿에 맞춰 정리하고, 사용자 승인을 받은 뒤 PR을 생성한다.

## 절대 규칙

- **PR 생성 전에 무조건 사용자 검수를 받는다.** base, 제목, 본문을 먼저 제시하고 사용자가 "올려줘", "진행해", "생성해"처럼 명시적으로 승인할 때만 `gh pr create`를 실행한다. `/pr`만 호출했을 때도 이 절차를 거친다. PR은 한번 만들면 팀 전체에 보이고 리뷰 요청이 나가므로 되돌리기 어렵다.
- **base를 `develop`으로 고정하지 않는다.** 아래 절차로 알아내고, 변경사항도 그 base 기준으로 모은다.
- 한 이슈를 여러 PR로 나눴으면 마지막 PR만 `close`를 쓴다.

## base 결정

### 기존 PR 확인

`/pr`은 PR을 새로 만들 때와 이미 있는 PR을 고칠 때 둘 다 불린다. 먼저 확인한다.

```bash
gh pr view --json number,baseRefName,url
```

PR이 있으면 새로 만들지 않고 고칠지 묻는다. PR이 없으면 `no pull requests found for branch`가 나오는데, 오류가 아니라 "아직 없다"는 뜻이다.

### base 찾기

base는 이 PR을 무엇과 비교할지 정하는 값이다. 이 브랜치를 갈라낸 브랜치가 base인데, git은 그 정보를 저장하지 않으므로 찾아야 한다.

내 브랜치에 커밋이 전부 들어 있는 브랜치를 모으고, 그중 **내 커밋이 가장 적게 남는 것**을 고른다. 그게 가장 최근에 갈라낸 브랜치다.

```bash
git fetch --prune origin
self="$(git branch --show-current)"
git branch -r --format='%(refname:short)' \
  | grep -vE "HEAD$|^origin/main$|^origin/$self\$" \
  | while read -r r; do
      git merge-base --is-ancestor "$r" HEAD 2>/dev/null \
        && printf '%s %s\n' "$(git rev-list --count "$r"..HEAD)" "$r"
    done | sort -n | head -5
```

현재 브랜치에서 실행하면 이렇게 나온다.

```
15 origin/feature/297-reservation-read-delete
19 origin/develop
```

15가 더 적으므로 base는 297 브랜치다. 차이 4개가 297 브랜치의 커밋이고, develop을 base로 두면 그 4개가 이 PR에 섞인다.

규칙 네 가지를 지킨다.

- **`--prune`을 붙인다.** 이 저장소는 머지와 함께 원격 브랜치를 지운다. prune하지 않으면 삭제된 브랜치가 목록에 남아 base로 뽑히고 PR 생성이 실패한다.
- **숫자가 같으면 `origin/develop`을 고른다.** `sort -n`은 동수일 때 이름순으로 정렬하므로 첫 줄을 그대로 쓰면 엉뚱한 브랜치가 온다.
- **앞 브랜치를 아직 푸시하지 않았으면 먼저 푸시한다.** 원격에 없는 브랜치는 base로 지정할 수 없다.
- **`origin/develop`이 목록에 없으면 멈춘다.** 아래 경우다.

### develop 반영 필요

이 저장소는 PR을 머지 커밋으로 합친다. 앞 PR이 머지되면 develop의 새 팁이 그 머지 커밋이 되고, 그 커밋은 내 브랜치에 들어 있지 않다. 그래서 develop이 목록에서 사라진다.

이때는 base를 고르지 않고 알린다.

```
origin/develop이 이 브랜치에 들어 있지 않습니다. 앞 PR이 머지된 뒤로 develop이 앞서갔습니다.

develop을 이 브랜치에 머지하거나 이 브랜치를 develop 위로 리베이스한 뒤
base 결정을 다시 실행합니다.
```

### 확인 요청

base가 `origin/develop`이 아니면 사용자에게 확인받는다.

```
base를 origin/feature/297-reservation-read-delete 로 판단했습니다.
이 브랜치 기준 내 커밋 15개, develop 기준 19개입니다.
develop을 base로 두면 앞 브랜치 커밋 4개가 섞입니다.

이대로 진행할까요?
```

## 작성 전 확인

본문을 쓰기 전에 네 가지를 모은다.

### 변경사항

base를 `BASE`라 하면 **`git log`는 두 점 `BASE..HEAD`, `git diff`는 세 점 `BASE...HEAD`를 쓴다.** `develop..HEAD`를 쓰지 않는다.

```bash
git log "$BASE"..HEAD --oneline
git diff "$BASE"...HEAD --stat
git status -sb
```

`git log BASE...HEAD`는 base 쪽 커밋까지 나열하므로 두 점과 세 점을 바꿔 쓰지 않는다. 이 범위에 나온 커밋이 이 PR의 작업 전부다.

### 문서 갱신 누락

코드 변경이 있는데 대응 문서 변경이 범위에 없으면 알린다. 어떤 변경이 어떤 문서를 무효화하는지는 [.agents/rules/docs.md](../../rules/docs.md)가 단일 소스다.

```
docs/reservation-cache-schema.md 갱신이 범위에 없습니다.
이번 변경에 reservation_booking_confirm.lua 수정이 포함돼 있습니다.

문서를 함께 고칠까요, 아니면 범위 밖 문제로 적을까요?
```

### 테스트

범위에 테스트 변경이 있는지 보고, 실행했는지 확인한다. 테스트가 필요한 변경의 판정은 [.agents/rules/test.md](../../rules/test.md)를 따른다.

기능 추가나 버그 수정인데 테스트 변경이 없으면 사용자에게 알린다. 실행하지 못한 검증이 있으면 리뷰어 참고 사항에 그 사실과 이유를 적는다.

### 범위 밖 문제와 배포 전 필수 작업

아래 "섹션별 작성 규칙"의 두 절에 무엇을 어디서 모으는지 적어뒀다. 본문을 쓰기 전에 모아둔다.

## 제목

기본은 이슈 제목 그대로다.

```bash
gh issue view {issue-number} --json title --jq '.title'
```

**한 이슈를 여러 PR로 나눌 때는 예외다.** 제목을 그대로 쓰면 두 PR의 제목이 같아져 목록에서 구분할 수 없다. 내용을 드러내고 스택 순서를 알 수 있게 쓰고, 끝에 `(#270 2/2)` 형태의 식별자를 붙인다. 그러면 체크리스트 줄도 바꿔야 한다.

```markdown
- [x] 제목을 확인했습니다. **이슈 제목과 다릅니다** — #270을 두 PR로 나눠 올리면서 #299와 제목이 같아지므로, 내용을 드러내고 스택 순서를 알 수 있게 `(#270 2/2)`를 붙였습니다. 이슈 원제목은 `{이슈 원제목}`입니다.
```

제목이 이슈와 다른데 체크리스트에 "동일함을 확인했습니다"를 체크해 두면 거짓이 된다. 다르면 다르다고 적고 이유와 원제목을 남긴다.

## 섹션별 작성 규칙

### 관련 Issue

이 PR로 이슈가 닫히면 `- close #{번호}`를 쓴다.

한 이슈를 여러 PR로 나눴고 이 PR이 마지막이 아니면 **`close`를 쓰지 않는다.** 번호만 적고 몇 번째 PR인지, 무엇이 남았는지, 어느 PR이 이슈를 닫는지 함께 적는다. `close`를 쓰면 이슈가 닫혀 남은 작업이 추적에서 사라진다.

닫기 키워드는 PR이 **기본 브랜치로 머지될 때만** 발동한다. 이 저장소의 기본 브랜치는 `develop`이다. base가 앞 브랜치인 스택 PR은 앞 브랜치로 머지될 때 닫히지 않고, 스택 전체가 develop에 닿을 때 닫힌다.

```markdown
- #270 (이 PR은 #270의 첫 번째 PR입니다. 결제 중 좌석 보호와 Recovery Worker는 두 번째 PR에서 다루고, 이슈는 그때 닫습니다.)
```

### 주요 변경 사항

- 커밋 메시지를 그대로 복사하지 않는다.
- 변경의 **목적과 의미**를 쓴다. 리뷰어가 코드를 읽기 전에 맥락을 잡을 수 있어야 한다.
- 한국어로, "-습니다" 완결형으로 쓴다.
- 표로 정리하면 이해가 빨라지는 항목(메트릭, API 스펙, 에러 코드 매핑, 설정값)은 마크다운 표로 넣는다.

### 배포 전 필수 작업

배포 전에 사람이 직접 해야 하는 작업이다. `ddl-auto`로 반영되지 않는 스키마 변경(컬럼 타입 변경, 컬럼 이름 변경, 기존 MySQL ENUM 컬럼에 값 추가, 데이터 이관), 새 설정값이나 시크릿, 수동으로 실행할 스크립트가 해당한다. 변경사항에 SQL 파일이 있으면 반드시 포함한다.

**주요 변경 사항 바로 다음**에 둔다. 맨 위에 두지 않는 이유는 읽는 순서다. 리뷰어는 이 PR이 무엇인지 모르는 상태로 본문을 위에서 아래로 읽는다. 맥락 없이 지시가 먼저 나오면 왜 그 SQL을 돌려야 하는지 모르는 채로 읽게 된다.

SQL과 명령은 코드 블록으로 그대로 적고, 적용 대상과 순서(예: ALTER 적용 후 배포)를 함께 적는다.

### 범위 밖 문제

작업 중 발견했지만 이 PR에서 고치지 않는 문제다. 설계 문서나 계획 문서의 "범위 밖" 절, 대화에서 "범위 밖", "후속", "별도 이슈"로 분류한 항목, 이번에 추가한 `TODO(#이슈)` 주석에서 모은다.

- **빠짐없이 적되 최대한 간결하게 쓴다.** 누락과 장황함 둘 다 피한다. 한 항목은 표의 한 줄이고, 각 칸은 한 문장을 넘기지 않는다. 문제 칸은 무엇이 문제인지만, 이유 칸은 왜 이번이 아닌지만 적는다. 설계 근거나 해결 방안은 해결 이슈에 있으므로 여기 옮기지 않는다.
- 항목이 많아도 줄이지 않는다. 길어지는 것은 항목 수 때문이어야 하고 항목당 길이 때문이 아니어야 한다.
- 해결할 이슈가 없는 항목이 있으면 PR을 만들기 전에 `/issue`로 등록할지 사용자에게 묻는다. 등록하지 않기로 했으면 해결 이슈 칸에 그 이유를 적는다.

```markdown
| 문제 | 이번 PR에서 다루지 않는 이유 | 해결 이슈 |
|---|---|---|
| FAILED 행에 실패 원인이 남지 않습니다 | 컬럼 추가가 필요해 마이그레이션과 함께 다룹니다 | #302 |
| 가상계좌 결제의 승인 지연을 처리하지 않습니다 | 설계가 정해지지 않았습니다 | #291 |
```

### 리뷰어 참고 사항과 추가 정보

- **리뷰어가 diff를 읽는 방식을 바꾸는 것만 적는다.** base가 평소와 다른 이유, 범위에 섞인 무관한 커밋, 한눈에 안 보이는 배선(Bean 구분, 이름 충돌 해소) 같은 것이다.
- 테스트 개수 보고(`750 tests 통과`)나 사소한 내부 선택의 정당화는 넣지 않는다. 리뷰어가 그걸 읽고 할 수 있는 일이 없고 CI가 이미 보여준다. 성실함의 증거를 남기는 자리가 아니다.
- 검증 결과를 적어야 한다면 리뷰어의 판단을 바꾸는 부분만 적는다. 무엇을 어떤 환경에서 실행해 확인했는지(예: 운영 SQL을 실제 DB 버전에 돌려 확인), 반대로 실행하지 못한 검증과 그 이유다.

## 검수

위에서 만든 결과를 이 형식으로 제시한다.

```
PR 생성 전 검수 요청

Base: {base}
범위: {base}..HEAD, 커밋 {N}개
제목: {이슈 제목}

본문:
---
{본문 전문}
---

이대로 PR을 생성할까요? 수정이 필요하면 말씀해주세요.
```

base가 develop이 아니면 범위 줄에 제외한 커밋 수를 함께 적는다 — `범위: feature/297-...-delete..HEAD, 커밋 15개 (develop 기준 19개, 앞 브랜치 4개 제외)`. 어느 범위를 골랐는지 보이지 않으면 검수할 수 없다.

해결 이슈가 없는 범위 밖 문제, 배포 전 필수 작업, 누락된 문서 갱신이 있으면 따로 짚어 알린다.

## 생성

승인 후 실행한다.

```bash
git push -u origin {branch-name}

gh pr create \
  --base {base} \
  --title "{이슈 제목}" \
  --body "$(cat <<'EOF'
{본문 전문}
EOF
)"
```

`--base`에 위에서 확인받은 값을 넣는다. 본문에 백틱과 `#`, `$`가 들어가므로 따옴표로 감싼 heredoc을 쓴다.

생성 후 URL을 알린다. base가 develop이 아니면 머지 순서를 함께 짚는다.

```
PR을 만들었습니다: {URL}

base가 {base}이므로 그 PR이 먼저 머지돼야 합니다.
앞 PR이 머지되면 이 PR의 base는 develop으로 자동 변경됩니다.
```

## 인자 처리

- `/pr` — 브랜치명에서 이슈 번호를 뽑는다. `feature/193-payment-metrics` → 193, `bug/45-fix-login-error` → 45. 이름 형식은 `/branch` SKILL.md가 단일 소스다
- `/pr 193` — 이슈 번호 193을 쓴다

## 예외 처리

### 이슈 번호 추출 불가

```
브랜치명에서 이슈 번호를 뽑지 못했습니다.
현재 브랜치: {branch-name}

이슈 번호를 알려주세요. 예: /pr 193
```

### base 대비 변경 없음

```
{base} 대비 변경사항이 없습니다. 커밋을 먼저 만들어주세요.
```

### 이슈 없음

```
GitHub 이슈 #{issue-number}를 찾을 수 없습니다. 번호를 확인해주세요.
```

### 생성 실패

| 오류 | 원인 | 처리 |
|---|---|---|
| `Base ref must be a branch` 계열 | base가 origin에 없다. 푸시 전이거나 머지와 함께 삭제됐다 | 앞 브랜치를 푸시하거나 base 결정을 다시 실행한다 |
| `No commits between A and B` | base를 잘못 잡았다 | base 결정 절차를 다시 실행한다 |
| `not logged into any GitHub hosts` 계열 | 로그인이 끊겼다 | `gh auth login` 실행을 요청한다 |

오류 문자열은 `gh` 버전에 따라 달라진다. 문자열로 매칭하지 말고 메시지를 읽어 위 세 원인 중 무엇인지 판단한다.

본문은 버리지 않는다. 원인만 처리하고 같은 본문으로 다시 실행한다.

## 릴리스 PR

**스택 PR은 릴리스 노트에 자동 수록되지 않는다.** `fill_pr_body.yml`은 머지 커밋에 연결된 PR 중 `base.ref === 'develop'`인 것만 남긴다. base가 앞 브랜치인 PR은 걸러진다. 그래서 스택의 **마지막 PR 주요 변경 사항에는 앞 PR 내용도 함께 요약한다.** 그러지 않으면 그 작업이 릴리스 노트에서 사라진다.

`develop` → `main` PR은 이 스킬이 다루지 않는다. `.github/workflows/fill_pr_body.yml`이 본문을 자동으로 덮어쓴다. 머지 커밋에서 PR 목록을 뽑아 라벨별로 분류하고 버전 라벨 체크리스트를 붙인다. 이 스킬로 본문을 써도 지워지므로 쓰지 않는다.
