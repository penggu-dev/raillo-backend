# Issue Implementation Plan

## 현재 상태
- 브랜치: !`git branch --show-current`
- 인자: `$ARGUMENTS`

## 전체 흐름

```
0. 준비      이슈 읽기 · 기존 계획 파일 확인
1. 탐색      관련 코드·문서 읽기
2. 계획      단계 분해 → .claude/plans/{N}.md 작성 → 사용자 승인
3. 단계 루프  [구현 → (/test) → 검증 → 검토 요청 → 승인 → /commit] × n
4. 마무리    /review → 반영 → /pr 안내
```

**절대 규칙**
- 계획 승인 전에는 코드를 수정하지 않는다.
- **한 단계가 끝나면 반드시 멈추고 검토를 요청한다.** 승인 없이 다음 단계로 넘어가거나 커밋하지 않는다.
- 단계 범위를 벗어나는 수정이 필요해지면 멈추고 계획 변경을 제안한다 (조용히 범위를 넓히지 않는다).
- 계획 파일의 상태는 실제와 항상 일치시킨다.

---

## 0. 준비

1. **이슈 번호**: `$ARGUMENTS` → 없으면 브랜치명 `label/N[-desc]`에서 추출 → 둘 다 없으면 물어본다.
2. **브랜치 확인**: `develop`/`main`이면 중단하고 안내한다.
   ```
   ⚠️ develop 브랜치입니다. 먼저 작업 브랜치를 만들어주세요 → /branch {이슈 설명} {N}
   ```
3. **이슈 읽기**: `gh issue view {N} --json title,body,labels,comments`. 체크리스트(`- [ ]`)는 단계 후보로 쓴다.
4. **재개 판단**: `.claude/plans/{N}.md`가 있으면 새로 만들지 않는다.
   - 파일을 읽고 `git log develop..HEAD --oneline`과 단계 상태를 대조한다.
   - `doing` 단계가 있으면 `git status`로 미커밋 변경을 확인하고 그 단계부터 이어간다.
   - 진행 현황을 요약해 보여주고 바로 3단계 루프로 들어간다.

## 1. 탐색

이슈 범위에 맞춰 필요한 만큼만 읽는다.
- 이슈가 언급한 클래스와 그 호출자·피호출자, 같은 도메인의 기존 패턴 (비슷한 Service/Validator/Test가 있으면 그것을 따른다)
- 루트 `AGENTS.md`의 **Situational References** 중 해당하는 문서 (예약/Lua → `reservation-cache-schema.md`, 캐시 → `train-cache-schema.md`, 좌석 충돌 → `seat-conflict-validation.md`, 에러 코드 → `error-code-convention.md`, 엔티티 → `domain-model.md`, 배포 → `deployment.md`)
- **재사용 후보**를 기록한다: 이미 있는 Validator, ErrorCode, Repository 쿼리, 유틸. 새로 만들기 전에 있는지 먼저 찾는다.

모호한 요구사항(선택지가 갈리고 코드로 결정할 수 없는 것)은 계획 작성 전에 질문한다.

## 2. 계획

### 단계 분해 규칙

- **한 단계 = 커밋 1개.** 그 단계만 적용해도 `./gradlew build`가 깨지지 않아야 한다.
- 권장 순서 (안쪽 → 바깥쪽):
  1. `raillo-domain` — Entity/VO/Enum, ErrorCode, 도메인 규칙 (+ 도메인 단위 테스트)
  2. `infrastructure` — Repository/QueryRepository, Redis, Lua
  3. `application` — Validator, Service, Calculator (+ 통합 테스트)
  4. `facade`·`presentation` — Facade, Controller, DTO, Swagger Doc
  5. `raillo-batch` / 설정 / 문서
- 기능 코드와 그 테스트는 **같은 단계**에 둔다 (테스트만 따로 미루지 않는다).
- 단계 수는 3~7개를 권장한다. 8개 이상이면 이슈 분할을 제안한다. 한 단계가 파일 10개 이상을 건드리면 더 쪼갠다.
- 각 단계에 적는다:
  - **목표** (한 문장), **변경 대상** (파일/클래스), **완료 조건** (검증 가능한 형태)
  - **테스트**: `필요` / `불필요` + 이유. 분기·상태 전이·계산·검증·동시성 로직이 있으면 필요. DTO·설정·문서·단순 위임이면 불필요.
  - **커밋 타입** (`feat`/`bug`/`refactor`/`test`/`chore`/`docs`)

### 계획 파일 `.claude/plans/{N}.md`

git에서 추적하지 않는 로컬 파일이다(`.gitignore`). 세션이 바뀌어도 이 파일로 이어간다.

```markdown
# #{N} {이슈 제목}

- 브랜치: {branch}
- 이슈: {이슈 링크}
- 상태: planning | in-progress | review | done

## 목표
{이슈가 해결하려는 문제와 완료 시 기대 결과, 2~3문장}

## 영향 범위
- {모듈/도메인/주요 클래스}
- 참고 문서: {읽은 docs}
- 재사용: {기존 Validator·유틸 등}

## 단계
| # | 목표 | 테스트 | 타입 | 상태 | 커밋 |
|---|------|-------|------|------|------|
| 1 | ... | 필요 | feat | todo | |
| 2 | ... | 불필요 | chore | todo | |

### 1. {목표}
- 변경: ...
- 완료 조건: ...
- 테스트: {케이스 개요 또는 불필요 이유}

### 2. ...

## 결정 기록
- {날짜} {결정과 이유 — 검토 중 바뀐 내용도 여기에}
```

상태 값: `todo` → `doing` → `done` (중간에 빠진 단계는 `skipped` + 이유).

### 계획 승인 요청

```
📋 #{N} 구현 계획 — {k}단계
{단계 표}

❓ 확인이 필요한 점: {있으면}
✅ 이대로 1단계부터 진행할까요? 단계 구성 수정도 가능합니다.
```

## 3. 단계 루프

각 단계마다:

1. 계획 파일에서 해당 단계를 `doing`으로 바꾼다.
2. **구현** — `AGENTS.md`의 Layer Rules·예외 3종·트랜잭션·파라미터 규칙을 지킨다. 주변 코드의 스타일(들여쓰기 탭, 주석 밀도, 네이밍)을 따른다.
3. **테스트** — `테스트: 필요`면 `/test` skill의 절차와 컨벤션으로 작성한다 (`/plan` 안에서는 케이스 목록 확인 없이 바로 작성).
4. **검증** — 이번 단계와 관련된 테스트를 실행한다.
   - 변경한 클래스의 테스트: `./gradlew :{모듈}:test --tests "{FQCN}"`
   - `raillo-domain`을 바꿨으면 의존 모듈 컴파일도 확인: `./gradlew compileJava compileTestJava`
   - 실패하면 고친 뒤 재실행한다. 이번 단계와 무관한 기존 실패라면 그 사실을 보고에 적는다.
   - Docker를 쓸 수 없는 환경이면 컴파일까지만 확인하고, 검토 요청의 테스트 칸에 실행할 명령과 `미실행 (Docker 불가)`를 적는다. 사용자가 실행 결과를 알려주면 승인으로 넘어간다.
5. **검토 요청** — 아래 형식으로 보고하고 **멈춘다.**

```
🔍 단계 {k}/{n} 검토 요청 — {목표}

📝 변경 파일
- {path} — {무엇을 왜}

💡 핵심 변경
- {리뷰어가 먼저 봐야 할 결정·트레이드오프 1~3개}

🧪 테스트
- {추가/수정한 테스트 n개, 실행 명령, 결과 — 불필요했으면 이유}

✉️ 커밋 메시지 (승인 시 바로 커밋)
{type}: {description} (#{N})

👉 승인하면 커밋 후 단계 {k+1}로 넘어갑니다. 수정할 점이 있으면 말씀해주세요.
```

6. **사용자 응답 처리**
   - **승인** ("좋아", "ㅇㅋ", "다음", "커밋해") → `/commit` 규칙(`/plan` 경유 모드)으로 이번 단계 파일만 stage해 즉시 커밋 → 계획 파일에 `done` + 커밋 해시 기록 → 다음 단계 시작.
   - **수정 요청** → 반영 → 4(검증)부터 다시 → 다시 검토 요청.
   - **계획 변경** → 계획 파일의 단계 표와 결정 기록을 갱신하고 변경점을 보여준 뒤 진행.
   - 승인 응답에 메시지 수정이 함께 오면 반영해서 커밋한다.

## 4. 마무리

모든 단계가 `done`이면:

1. 계획 파일 상태를 `review`로 바꾸고 `/review` skill을 실행한다 (범위: `develop...HEAD`).
2. 리뷰 결과에서 사용자가 반영하기로 고른 항목은 **새 단계**로 계획 파일에 추가하고, 같은 단계 루프로 처리한다.
3. 반영이 끝나면 (또는 반영할 항목이 없으면):
   ```
   ✅ #{N} 모든 단계 완료
   {단계 표 — 커밋 해시 포함}

   👉 다음: /pr 로 PR을 생성합니다. 진행할까요?
   ```
4. 사용자가 원하면 `/pr` skill을 실행한다 (`/pr`은 자체 검수 절차를 거친다). 완료 후 계획 파일 상태를 `done`으로.

## 예외 처리

- **이슈 조회 실패** (`gh` 미인증·없는 번호): 오류를 보여주고 이슈 내용을 직접 붙여달라고 요청한다.
- **브랜치에 이미 계획 외 커밋이 있음**: 커밋 목록을 보여주고 계획에 반영할지 묻는다.
- **미커밋 변경이 있는 상태로 시작**: 이번 이슈 작업인지 확인한다. 무관하면 건드리지 않고 커밋에서 제외한다.
- **빌드/테스트가 계속 실패** (2회 수정 후에도): 원인 분석과 선택지를 보고하고 사용자 결정을 기다린다.
