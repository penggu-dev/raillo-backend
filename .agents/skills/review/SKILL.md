# Isolated Code Review

## 현재 상태
- 브랜치: !`git branch --show-current`
- 인자: `$ARGUMENTS`

## 원칙

1. **메인 세션은 리뷰하지 않는다 — 조율만 한다.** 코드를 작성한 세션은 자기 의도를 알기 때문에 확증 편향이 생긴다. 실제 판단은 대화 이력이 없는 서브에이전트가 한다.
2. 서브에이전트에게는 **diff 범위 · 이슈 원문 · 담당 체크리스트만** 넘긴다. "이렇게 짠 이유", 구현 중 논의, 계획 파일의 설계 의도는 넘기지 않는다. (이슈 원문은 요구사항 충족 여부 판단에 필요하므로 넘긴다.)
3. **높은 신호만 보고한다.** 확인되지 않은 지적, 취향, 기존 문제는 버린다. 지적 0건도 정상 결과다.
4. **리뷰는 제안만 한다.** 코드 수정·커밋은 하지 않는다.

## 1. 범위 결정

| 인자 | diff 범위 |
|------|----------|
| (없음) | `develop...HEAD` — 브랜치 전체 커밋 |
| `--staged` | `git diff --cached` |
| `--working` | `git diff HEAD` — 커밋 안 된 변경 전체 (중간 리뷰용) |
| `A..B` / `A...B` | 그대로 |
| 경로 | `develop...HEAD -- <경로>` |

다음을 수집한다 (병렬 실행):
- `git diff {범위} --stat` 와 `--name-only` — 변경 파일 목록
- `git log {범위} --oneline` (커밋 범위일 때)
- 이슈 번호(브랜치명 `label/N-...`) → `gh issue view N --json title,body` (실패하면 이슈 없이 진행)

diff가 비어 있으면 `⚠️ 리뷰할 변경이 없습니다.`로 종료한다.

**규모 판단**: 변경 파일이 3개 이하이고 diff가 200줄 미만이면 리뷰어 A·B·C를 **하나의 서브에이전트**로 합쳐 실행한다(체크리스트 세 개를 모두 전달). 그보다 크면 아래처럼 병렬로 나눈다.

## 2. 병렬 리뷰 (서브에이전트 3개, 한 메시지에서 동시 실행)

[reviewers.md](reviewers.md)를 읽어 **공통 지침 + 각 리뷰어 체크리스트**로 프롬프트를 만든다. `{DIFF_RANGE}`, `{CHANGED_FILES}`, `{ISSUE}` 자리표시자를 채운다 (검증자는 `{FINDINGS}`에 합친 후보 JSON을 index와 함께 넣는다). diff 본문은 프롬프트에 붙이지 않는다 — 에이전트가 `git diff {DIFF_RANGE}`로 직접 읽고 주변 코드까지 탐색하게 한다.

| 리뷰어 | 관점 | subagent_type |
|-------|------|---------------|
| A | 컨벤션 — AGENTS.md 규칙 위반 (원문 인용 필수) | `general-purpose` |
| B | 정확성 — 로직·트랜잭션·동시성·Redis/Lua·캐시 계약 | `general-purpose` |
| C | 테스트 — 누락된 분기, 약한 검증, 테스트 컨벤션 | `general-purpose` |

각 에이전트는 reviewers.md의 **고정 형식**(JSON 배열)으로 지적을 반환한다.

## 3. 검증 패스 (서브에이전트 1개)

1. 세 리뷰어의 결과를 합친다. `confidence < 50`은 버린다.
2. 같은 `file:line` + 같은 원인은 하나로 합친다 (높은 confidence·심각도 유지).
3. 남은 항목이 0개면 검증 없이 5로 간다.
4. 남은 항목을 reviewers.md의 **검증자 프롬프트**로 새 `general-purpose` 서브에이전트에 넘긴다. 검증자는 실제 코드를 읽고 각 항목을 `CONFIRMED` / `REJECTED`로 판정한다 (근거·실패 시나리오를 재현할 수 없으면 REJECTED).
5. `CONFIRMED`만 남긴다.

## 4. 보고

메인 세션은 검증 결과를 그대로 정리만 한다 (항목을 추가·삭제·완화하지 않는다).

```
🔎 리뷰 결과 — {범위} ({파일 n개, +a/-b})
리뷰어: 컨벤션 · 정확성 · 테스트 → 후보 {x}건 → 검증 통과 {y}건

| # | 심각도 | 분류 | 위치 | 내용 |
|---|-------|------|------|------|
| 1 | 🔴 blocker | 정확성 | [Foo.java:42](path:42) | 한 문장 요약 |
| 2 | 🟠 major | 컨벤션 | ... | ... |
| 3 | 🟡 minor | 테스트 | ... | ... |

### 1. {요약}
- 근거: {규칙 인용 또는 코드 근거}
- 실패 시나리오: {입력/상태 → 잘못된 결과}
- 수정 제안: {구체적으로, 필요하면 짧은 코드}

...

👉 반영할 항목 번호를 알려주세요. (예: "1, 3 반영")
```

지적이 0건이면:
```
✅ 리뷰 결과 — {범위}: 확인된 문제 없음 (후보 {x}건 모두 검증 단계에서 제외)
```

심각도 기준:
- 🔴 **blocker** — 잘못된 결과·데이터 손상·좌석 중복 점유·트랜잭션 누락·컴파일 실패. 머지 전 반드시 수정
- 🟠 **major** — AGENTS.md 명시 규칙 위반, 변경된 핵심 분기의 테스트 누락, 장애 시 복구 불가
- 🟡 **minor** — 명확한 개선이지만 동작에는 영향 없음

## 5. 후속

- `/plan` 흐름에서 호출됐으면: 사용자가 고른 항목을 계획 파일의 새 단계로 추가하고 단계 루프로 돌아간다.
- 단독 호출이면: 사용자가 고른 항목을 수정하고, 끝나면 `/commit`을 안내한다.
- 사용자가 지적에 반대하면 그 판단을 따른다. 다시 주장하지 않는다.
