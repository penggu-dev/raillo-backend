결제 승인 흐름

Payment 승인은 세 단계로 나뉜다. 1단계 승인 시작, 2단계 Toss 호출, 3단계 승인 확정. 실제 DB 트랜잭션은 TX A(1단계 안의 짧은 REQUIRES_NEW)와 TX B(3단계 전체) 두 개이며 Toss 호출은 트랜잭션 밖에서 실행된다. Toss 승인 실패는 예약과 Payment 상태에 영향을 주지 않고 실패한 PaymentAttempt만 남긴다. Payment.paymentKey는 승인 확정 시에만 저장한다.

결제 도메인 상태 계층

Toss 승인 실패는 예약과 Payment 상태에 영향을 주지 않는다. 실패한 PaymentAttempt만 FAILED로 마킹하고 Payment는 PENDING을 유지한다. 같은 Payment 위에 새 PaymentAttempt를 얹어 재시도할 수 있다. 예약의 회수는 예약 TTL(10분) 만료 또는 유저 명시 취소 시점에만 일어난다.

재시도 가능한 실패 허용

카드 승인 거절, 한도 초과 등 재시도 여지가 있는 실패에서도 유저가 다른 카드로 재시도할 수 있어야 한다. 승인 성공/실패는 PaymentAttempt 단위의 이벤트이며 Payment와 예약의 소유권을 결정하지 않는다. 좌석 회수는 예약 TTL이라는 시간 제약으로 충분하고, 결제 시점의 별도 좌석 잠금 계층은 두지 않는다.

결제 승인 3단계

결제 승인 요청(POST /api/payments/confirm)은 세 단계로 나뉜다. 1단계 (승인 시작)는 PaymentApprovalStarter.start()가 조회·검증을 tx 없이 수행한 뒤, 그 끝에서 PaymentAttemptManager.startApprovalInNewTransaction()을 REQUIRES_NEW로 짧게 열어 PaymentAttempt를 IN_PROGRESS로 커밋한다(이것이 TX A). 2단계 (Toss 호출)는 DB 트랜잭션 밖에서 이뤄진다. 3단계 (승인 확정)는 PaymentApprovalFinalizer.finalizeApproval() 메서드 전체가 하나의 @Transactional이며, 승인 결과를 Payment·PaymentAttempt·Order·Booking·Outbox에 한 번에 커밋한다(이것이 TX B).

TX A 커밋 항목
# PaymentAttemptManager.startApprovalInNewTransaction()
INSERT INTO payment_attempt (
  payment_id, attempt_id, attempt_type,
  status, payment_key
) VALUES (
  ?, '<SHA256 파생>', 'APPROVAL',
  'IN_PROGRESS', ?
);
# attempt_id는 unique 제약 → 같은 세션 재요청은 DB에서 dedup
TX B 커밋 항목
# PaymentApprovalFinalizer.finalizeApproval()
UPDATE payment SET status = 'PAID',
  payment_method = ?, payment_key = ?, paid_at = NOW();
UPDATE payment_attempt SET status = 'SUCCEEDED';
UPDATE `order` SET status = 'ORDERED';
INSERT INTO booking, seat_booking, ticket ...;
INSERT INTO payment_outbox (
  type, deduplication_key, payload, status
) VALUES (
  'BOOKING_CONFIRMED', 'payment:{id}:booking-confirmed',
  '{...}', 'PENDING'
);
후속 처리 R → B (예약 → 예매 좌석 field 전환)

아웃박스의 BOOKING_CONFIRMED 이벤트는 Redis 좌석 field를 R:reservationId(예약)에서 B:bookingId(예매)로 전환하는 후속 처리에 사용된다. 이번 브랜치에서는 처리기가 미등록 상태로 이벤트는 PENDING으로 보존되고, 후속 PR에서 처리기를 활성화한다. 사용자 응답은 이 후속 처리를 기다리지 않는다.

Toss 응답별 분기

Toss는 세 종류로 응답한다. 2xx는 성공 확정, 4xx는 명확한 실패, 5xx/타임아웃은 결과 불명이다. 각 응답은 서로 다른 처리 경로를 탄다.

IN_PROGRESS 회복 경로

5xx/타임아웃으로 IN_PROGRESS로 남은 PaymentAttempt는 두 경로로 회복한다. 온라인은 유저가 같은 결제창에서 재시도할 때 서버가 attemptId dedup으로 기존 시도를 찾아 Toss에 실제 상태를 조회하고 로컬을 정정한다. 배치는 Recovery Worker(#270)가 유저 요청 없이 오래 남은 IN_PROGRESS PaymentAttempt를 대사한다. 두 경로 모두 동일한 GET /v1/payments/{paymentKey}로 Toss 상태를 확인한다.

온라인 회복 — 유저 재시도

배치 회복 — Recovery Worker (#270)

유저 재요청이 없어도 오래 남은 IN_PROGRESS PaymentAttempt는 Recovery Worker가 주기적으로 대사한다. 각 시도의 payment_key로 Toss에 GET /v1/payments/{paymentKey}를 호출하고, 응답 상태에 맞춰 로컬 PaymentAttempt와 Payment를 정정하거나 후속 아웃박스 이벤트를 발행한다. 이 워커의 폴링·리스·재시도 정책은 별도 이슈(#270)에서 다룬다.

attemptId · 서버 파생 idempotency key

클라이언트는 attemptId를 보내지 않는다. 서버가 paymentKey에서 SHA256으로 파생하고, PaymentAttempt.attempt_id의 unique 제약이 서버 측 idempotency 역할을 한다.

파생 규칙 (PaymentAttemptIds.forApproval)
// 승인 attempt
public static String forApproval(String paymentKey) {
  return sha256Hex("apv:" + paymentKey);
}

// 취소 attempt (부분 취소 지원)
public static String forCancellation(String paymentKey, int sequence) {
  return sha256Hex("cnl:" + paymentKey + ":" + sequence);
}
  • Toss가 결제창 세션당 새 paymentKey를 발급한다. 유저가 결제창을 새로 열면 새 paymentKey → 새 attemptId → 새 PaymentAttempt.
  • 같은 결제창의 더블 클릭, 네트워크 재전송은 같은 paymentKey → 같은 attemptId → DB unique로 dedup된다.
  • 클라이언트가 attemptId를 직접 관리할 필요가 없다. Toss 결제창은 온라인 세션이므로 프론트 offline queue 시나리오가 성립하지 않는다.
  • 취소는 부분 취소가 여러 번 가능하므로 sequence를 더해 매번 다른 attemptId를 만든다. 승인 attempt와도 hash prefix(apv: vs cnl:)로 구분된다.

Payment.paymentKey 저장 시점

Payment.payment_key는 승인 확정 시에만 저장한다. 취소·환불에서 Toss에 넘기는 결제 식별자 역할을 한다. 승인 처리 도중 회복에 필요한 저장된 paymentKey는 PaymentAttempt.payment_key가 담당하며 TX A 시점에 이미 저장된다.

두 컬럼의 역할 분리
// Prepare 시
INSERT payment (payment_key = NULL, status = PENDING)

// TX A - Toss 호출 전 (회복용으로 미리 저장)
INSERT payment_attempt (
  payment_key = '<결제창의 paymentKey>',
  status = IN_PROGRESS
)

// TX B - Toss 승인 성공 후 (확정된 paymentKey 저장)
UPDATE payment
  SET payment_key = '<성공한 paymentKey>',
      status = PAID
// ↑ 취소/환불은 이 값 하나로 Toss에 요청
두 컬럼의 역할 분리

3단계 승인 구조에서 1단계 마지막의 TX A가 PaymentAttempt를 커밋한 뒤 Toss를 호출한다. Toss 응답이 유실되거나 프로세스가 종료되어도 PaymentAttempt.payment_key로 Toss에 상태를 조회할 수 있다. Payment.payment_key는 확정된 paymentKey만 표현하므로 확정 전에는 NULL이며, 취소·환불은 이 값 하나로 처리한다.

동시성 제어

낙관적 락(@Version)은 사용하지 않는다. 비관적 락과 UNIQUE 제약 조합으로 처리한다.

Payment 잠금 시간축

confirm 요청 하나의 처리 시간 중 Payment 행이 잠기는 구간을 표시했다. Toss 호출 구간은 잠금이 없어서 응답이 오래 걸려도 다른 요청이 같은 Payment를 조회·처리할 수 있다.

왜 낙관적 락을 안 쓰나

Payment는 짧은 트랜잭션에서만 쓰기가 일어나고, 동시성 방어는 PaymentAttempt.attempt_id UNIQUE + Payment PENDING 상태 검증 조합으로 이미 커버된다. 아웃박스 폴링은 다수 워커의 동시 선점이 필요하므로 SKIP LOCKED가 자연스럽다. 낙관적 락을 얹으면 @Version 관리·retry 처리 부담만 늘어난다.
