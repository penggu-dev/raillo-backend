# 요구사항 초안 (검토용)

> 이 문서는 확정 전 초안이다. 확정되면 도메인별 `docs/{domain}/requirements.md`로 옮기고 이 파일은 지운다.

## 읽는 법

- 출처는 코드와 테스트(`@DisplayName`)뿐이다. 기존 문서는 참고하지 않았다.
- 기준 커밋: 예약, 주문, 결제, 예매는 `eca6a49b`(develop #308 반영)로 다시 확인했다. 인증, 회원, 열차는 `7e75d363` 기준이며 그 사이 바뀐 코드가 없다.
- 요구사항은 구현 용어가 아니라 사용자와 비즈니스 관점으로 쓴다. 결정된 목표 동작을 적고, 지금 코드와 다르면 상태로 표시한다.
- 각 도메인은 세 부분으로 나뉜다.

| 구분 | 뜻 | 할 일 |
|---|---|---|
| **요구사항** | 목표 동작. 코드가 뒷받침하거나 결정으로 정한 것 | 맞는지 확인하고, 틀리면 고친다 |
| **Q. 확인 필요** | 의도를 알 수 없는 동작, 빠진 기능, 결정에서 새로 생긴 질문 | 답을 정한다 |
| **P. 추가 제안** | 지금 코드에 없지만 넣으면 좋다고 판단한 것 | 채택, 보류, 기각을 정한다 |

상태 표시: ✅ 구현됨 / ⚠️ 일부만 구현됨 / 🔜 결정됨, 구현 예정 / ⏸ 보류 / ❌ 도메인 모델에만 있고 쓰는 곳 없음

## 1. 인증 (AUTH)

### 요구사항

| ID | 요구사항 | 상태 |
|---|---|---|
| AUTH-01 | 회원가입에는 이름, 휴대폰 번호(하이픈 없는 숫자 11자리), 비밀번호, 이메일, 생년월일(YYYY-MM-DD), 성별(M/W)이 필요하다. 이미 쓰는 이메일로는 가입할 수 없다 | ✅ |
| AUTH-02 | 로그인은 회원번호와 비밀번호로 한다 | ✅ |
| AUTH-03 | 로그인하면 액세스 토큰(30분)과 리프레시 토큰(7일)을 받는다 | ✅ |
| AUTH-04 | 리프레시 토큰으로 액세스 토큰을 다시 받을 수 있다. 서버에 저장된 리프레시 토큰과 다르면 거부한다 | ✅ |
| AUTH-05 | 로그아웃한 토큰은 다시 쓸 수 없다. 리프레시 토큰이 이미 만료됐어도 로그아웃은 성공한다 | ✅ |
| AUTH-06 | 이메일 인증 코드는 6자리 숫자이고 5분 동안 유효하다 | ✅ |
| AUTH-07 | 로그인 없이 쓸 수 있는 기능은 가입, 로그인, 토큰 재발급, 이메일 인증, 회원번호 찾기, 비밀번호 찾기, 열차 조회뿐이다. 나머지는 로그인이 필요하다 | ✅ |
| AUTH-08 | 비밀번호 찾기 인증을 마치면 5분짜리 임시 토큰을 받고, 이 토큰으로는 비밀번호 재설정만 할 수 있다 | ✅ |

| # | 현재 동작 | 질문 |

### P. 추가 제안

| # | 제안 | 이유 |
|---|---|---|

## 2. 회원 (MEM)

> 결정 (2026-10-09): 우선순위가 낮아 현행 유지. 아래 Q는 보류한다.

### 요구사항

| ID | 요구사항 | 상태 |
|---|---|---|
| MEM-01 | 회원번호는 가입일(yyyyMMdd)과 그날의 가입 순번 4자리로 만든다. 예: `202610090001` | ✅ |
| MEM-02 | 회원은 자기 정보를 조회할 수 있다 | ✅ |
| MEM-03 | 회원번호를 잊으면 이름과 휴대폰 번호로 회원을 확인하고, 등록된 이메일로 받은 인증 코드를 확인해 찾을 수 있다 | ✅ |
| MEM-04 | 비밀번호를 잊으면 회원번호와 이름을 확인하고 이메일 인증을 거쳐 재설정한다. 이름이 다르면 거부한다 | ✅ |
| MEM-05 | 이메일은 새 이메일로 받은 인증 코드를 확인해야 바뀐다. 지금과 같은 이메일, 다른 회원이 쓰는 이메일, 이미 변경이 진행 중인 이메일(5분)은 거부한다 | ✅ |
| MEM-06 | 휴대폰 번호를 바꿀 수 있다. 지금과 같은 번호, 다른 회원이 쓰는 번호는 거부한다 | ✅ |
| MEM-07 | 비밀번호를 바꿀 수 있다. 지금과 같은 비밀번호는 거부한다 | ✅ |
| MEM-08 | 탈퇴하면 즉시 로그아웃되고 회원 정보는 숨겨진다. 3년이 지나면 배치가 영구 삭제한다 | ✅ |
| MEM-09 | 탈퇴한 회원은 결제를 진행할 수 없다 | ✅ |

### Q. 확인 필요

| # | 현재 동작 | 질문 |
|---|---|---|
| MEM-Q1 | **탈퇴하면 그 회원의 예매가 DB에서 바로 삭제된다.** 회원은 3년간 남기는데 예매는 지운다. 결제와 주문 기록은 남고, 환불은 없다 | 결제를 마친 예매가 있는 회원의 탈퇴를 어떻게 처리하나? (탈퇴 막기, 환불 후 탈퇴, 예매 보존) |
| MEM-Q2 | 비밀번호를 바꿀 때 현재 비밀번호를 확인하지 않는다 | 현재 비밀번호 확인이 필요한가? |
| MEM-Q3 | 하루 순번이 4자리라 하루 가입자가 9,999명을 넘으면 회원번호 형식이 깨진다 | 상한을 넘으면 어떻게 하나? |

## 3. 열차 조회와 운행 데이터 (TRN)

### 요구사항

| ID | 요구사항 | 상태 |
|---|---|---|
| TRN-01 | 운행 캘린더는 오늘부터 1개월 동안 날짜별 운행 여부와 공휴일 여부를 보여준다. 자정이 지나면 새로 계산한다 | ✅ |
| TRN-02 | 열차는 출발역, 도착역, 운행일, 승객 수(1~9명), 출발 희망 시각(정시)으로 검색한다. 운행일은 오늘부터 1개월 이내다 | ✅ |
| TRN-03 | 검색 결과는 희망 시각 이후 출발하는 열차를 시간순으로 보여주고 페이지로 나눈다 | ✅ |
| TRN-04 | 오늘 날짜를 검색하면 지금부터 5분 뒤 이후에 출발하는 열차만 보인다. 예약 마감 규칙(RSV-07)과 같은 기준이다 | ✅ (TRN-Q3) |
| TRN-05 | 검색 결과에는 일반실과 특실 각각의 운임과 예약 가능 여부(잔여석이 승객 수 이상인지)가 나온다 | ✅ |
| TRN-06 | 잔여석은 전체 좌석에서 검색 구간과 겹치는 확정 예매와 예약 중인 좌석을 뺀 수다. 같은 좌석은 한 번만 뺀다. 구간이 겹치지 않는 예매와 예약은 빼지 않는다 | ✅ |
| TRN-07 | 객차 목록은 잔여석이 있는 객차만 보여주고, 승객 수를 수용하는 객차 중 가운데 객차를 추천한다. 수용하는 객차가 없으면 첫 번째 객차를 추천한다 | ✅ |
| TRN-08 | 좌석 상세는 객차의 좌석마다 선택 가능 여부를 보여준다 | ✅ |
| TRN-09 | 운임은 구간(방향 구분)과 객차 등급으로 정해진다. 승객 유형별 할인율은 어른 0%, 어린이 40%, 유아 75%, 경로 30%, 중증 장애인 50%, 경증 장애인 30%, 국가유공자 50%다 | ✅ |
| TRN-10 | 시간표와 운임표는 엑셀 파일에서 읽어 들인다 | ✅ |
| TRN-11 | 운행 스케줄은 배치로 만든다. 일일 Job은 다음 날짜 하나, 월간 Job은 한 달 뒤까지 만든다. 같은 날짜로 다시 실행해도 중복으로 만들지 않는다 | ✅ |
| TRN-12 | 스케줄을 만들면 곧바로 예약용 기준정보 캐시에 올린다. 운행 캐시는 운행일 + 2일까지 유지한다. 캐시만 다시 채우는 Job도 따로 있다 | ✅ |

### Q. 확인 필요

| # | 현재 동작 | 질문 |
|---|---|---|
| TRN-Q1 | 운행 취소와 지연 상태가 있고 검색과 예약에 반영되지만, 운행을 취소하거나 지연시키는 기능(API, 배치)은 없다 | 운행 상태 변경이 필요한가? 필요하면 누가 어떻게 하나? (관리자 API, 외부 연동) |
| TRN-Q2 | 할인을 곱한 운임을 반올림하지 않는다. 예: 43,210원에 유아 할인 → 10,802.5원 | 원 단위 처리 규칙(올림, 내림, 반올림, 10원 단위)이 있나? |
| TRN-Q3 | 예약 마감이 출발 10분 전으로 바뀐다(RSV-07). 검색은 여전히 5분 뒤 이후 열차를 보여주므로, 출발 5~10분 전 열차는 검색되지만 예약할 수 없다 | 검색 기준도 10분으로 맞출까? |
