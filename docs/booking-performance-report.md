# 예약 API 성능 개선 보고서

> 이 문서는 EKS 환경에서 본격적인 부하 테스트를 진행하기 전, 로컬 환경에서 개선 방향이 실제로 효과가 있는지 확인하기 위해 작성한 초안이다.  
> 최종 포트폴리오에는 EKS에서 다시 측정한 결과를 기준으로 수치와 설명을 보완한다.

## 기존 문제점

기존 v1 예약 API는 동시에 같은 좌석을 예약하려는 요청을 막기 위해 MySQL의 비관적 락을 사용했다. 비관적 락은 쉽게 말해, 한 요청이 특정 데이터를 사용하는 동안 다른 요청은 그 데이터 접근을 기다리게 만드는 방식이다.

문제는 이 서비스의 좌석 예약이 단순히 “좌석 하나를 누가 차지했는가”로 끝나지 않는다는 점이다. 열차 좌석은 구간에 따라 재사용될 수 있다. 예를 들어 같은 좌석이라도 `서울 -> 대전` 예약과 `대전 -> 부산` 예약은 구간이 겹치지 않으므로 함께 존재할 수 있다.

하지만 v1 구조에서는 좌석 단위로 락 경합이 발생하기 쉬웠다. 같은 좌석이라는 이유로 실제로는 충돌하지 않는 구간까지 영향을 받을 수 있었고, 예약 요청이 몰릴수록 DB에서 기다리는 시간이 길어졌다.

이로 인해 다음 문제가 발생했다.

- 관련 없는 구간까지 함께 영향을 받는 과도한 락 대기
- 요청이 몰릴수록 응답 시간이 급격히 증가
- 일부 요청에서 DB deadlock으로 인한 500 오류 발생
- 임시 예약 만료 처리를 스케줄러가 주기적으로 처리하면서 서버와 DB에 추가 부하 발생

결국 결제 전 좌석 선택 단계에서 MySQL이 너무 많은 책임을 갖고 있었고, 사용자가 몰리는 상황에서는 DB 락 대기가 성능 병목으로 이어졌다.

## 테스트 진행

로컬 테스트는 v1 예약 API와 개선 후 develop 예약 API를 같은 사용자 행동 기준으로 비교했다. 목표는 운영 환경 수준의 최종 수치를 얻는 것이 아니라, 구조 변경이 실제로 성능 개선 방향으로 이어지는지 먼저 확인하는 것이었다.

테스트는 다음 상황을 가정했다.

- 동시에 100명의 사용자가 예약을 시도한다.
- 전체 좌석 중 약 30%는 이미 예약된 상태로 만들어둔다.
- 나머지 좌석과 이미 예약된 좌석을 섞어서 계속 예약 요청을 보낸다.
- 즉, 일부 요청은 성공하고 일부 요청은 좌석 충돌로 실패하는 상황을 만든다.
- 각 테스트를 다시 실행하기 전에는 예약/결제 데이터를 초기화하고 Redis 데이터도 비운다.
- v1과 develop을 각각 3번씩 실행해 중간값을 비교한다.

테스트를 진행하면서 다음 문제도 발견했다.

첫째, DB를 초기화하지 않고 같은 테스트를 여러 번 실행하면 뒤로 갈수록 이미 예약된 좌석이 많아져 대부분의 요청이 충돌로 끝났다. 이 경우 1회차와 2회차, 3회차의 조건이 달라지므로 공정한 비교가 되지 않았다. 그래서 각 실행 전마다 예약 데이터를 초기화하도록 정리했다.

둘째, develop은 출발 시간이 지난 열차에 대해 예약을 막고 있었다. 테스트 준비 스크립트가 과거 스케줄을 선택하면 모든 요청이 `TRAIN_402`로 실패했다. 이 문제를 막기 위해 현재 시각보다 충분히 이후에 출발하는 열차만 선택하도록 수정했다.

셋째, v1에서는 요청이 몰릴 때 간헐적으로 500 오류가 발생했다. 로그를 확인해보니 MySQL deadlock과 예약 엔티티 조회 실패가 확인됐다. 이는 단순히 “좌석이 이미 예약됨”이라는 정상적인 충돌 응답이 아니라, 서버 내부 오류로 처리된 케이스였다.

## 변경

개선 후 구조에서는 결제 전 임시 예약과 결제 후 확정 예약의 책임을 분리했다.

- `PendingBooking`: 결제 전 임시 예약
- `SeatBooking`: 결제 완료 후 확정 예약 데이터

기존에는 결제 전 좌석 선택 단계에서도 MySQL이 많은 처리를 담당했다. 개선 후에는 결제 전 임시 좌석 선점은 Redis가 맡고, 결제 완료 후 확정된 예매 데이터만 MySQL에 저장한다.

Redis는 짧은 시간 동안 유지되는 임시 데이터를 다루기에 적합하다. PendingBooking은 결제 전까지만 의미가 있고, 일정 시간이 지나면 자동으로 만료되어야 한다. 이 특성은 Redis의 만료 시간 기능과 잘 맞는다.

또한 좌석 선점 충돌 처리는 Redis Set과 Lua Script를 사용했다. 쉽게 말해, 여러 사용자가 동시에 같은 좌석을 잡으려고 해도 Redis 안에서 한 번에 충돌 여부를 확인하고 선점까지 처리하도록 만든 것이다. 중간에 다른 요청이 끼어들어 상태가 꼬이는 일을 막을 수 있다.

변경 후 역할은 다음과 같이 나뉜다.

- 결제 전 좌석 선택: Redis에서 임시 선점 처리
- 결제 전 좌석 충돌 판단: Redis Set과 Lua Script로 빠르게 확인
- 임시 예약 만료: Redis 만료 시간으로 자동 처리
- 결제 완료 후 확정 예약: MySQL에 SeatBooking으로 저장

이 구조의 핵심은 MySQL을 버리는 것이 아니다. MySQL은 확정된 예매 데이터를 안전하게 보관하고, Redis는 짧은 시간 동안만 필요한 임시 선점 처리를 담당한다. 각 저장소가 잘하는 역할만 맡도록 분리한 것이다.

## 변경 후 테스트 진행

로컬 테스트 결과, 개선 후 develop은 v1보다 같은 시간 동안 훨씬 많은 요청을 처리했고, 응답 시간도 크게 줄었다.

중간값 기준 결과는 다음과 같다.

| 항목 | v1 | develop | 변화 |
|---|---:|---:|---:|
| 초당 처리 요청 수 | 50.54건/초 | 268.64건/초 | 431.58% 증가 |
| 평균 응답 시간 | 1,518.13ms | 297.13ms | 80.43% 감소 |
| p90 응답 시간 | 1,985.78ms | 388.76ms | 80.42% 감소 |
| p95 응답 시간 | 2,109.88ms | 407.54ms | 80.68% 감소 |
| p99 응답 시간 | 2,304.71ms | 511.53ms | 77.81% 감소 |

여기서 `p90`은 전체 요청 중 90%가 해당 시간 안에 처리됐다는 의미이고, `p95`는 전체 요청 중 95%, `p99`는 전체 요청 중 99%가 해당 시간 안에 처리됐다는 의미다. 평균만 좋아지는 경우에는 일부 사용자가 여전히 오래 기다릴 수 있다. 하지만 이번 결과에서는 요청이 몰렸을 때 느리게 처리되는 요청의 응답 시간도 함께 줄었다.

v1은 요청이 몰리면 일부 요청이 2초 이상 대기했고, 간헐적으로 500 오류도 발생했다. 반면 develop은 더 많은 요청을 처리하면서도 대부분의 요청을 0.5초 안팎에서 처리했다.

좌석 충돌 응답은 여전히 발생했다. 하지만 이 충돌은 서버 오류가 아니라 “이미 다른 사용자가 해당 좌석 구간을 선점했다”는 정상적인 도메인 결과다. 중요한 차이는 v1에서는 일부 충돌 상황이 서버 내부 오류로 번졌지만, develop에서는 충돌을 정상 응답으로 처리했다는 점이다.

이번 로컬 테스트만으로 운영 환경 성능을 단정할 수는 없다. 다만 다음 개선 방향은 확인할 수 있었다.

- 결제 전 좌석 선택에서 DB 락 대기 감소
- 요청이 몰릴 때 p90, p95, p99 응답 시간 개선
- 임시 예약 만료 처리를 스케줄러가 아닌 Redis 만료 시간으로 처리
- 고경합 상황에서 서버 내부 오류 감소

최종적으로는 EKS 환경에서 v1과 develop을 서로 다른 노드에 배치하고, 같은 조건으로 다시 측정해 포트폴리오에 사용할 최종 수치를 정리한다.

## 문제점

Redis를 사용하면서 새로운 운영상 주의점도 생겼다. 개선 후 구조에서는 결제 전 임시 예약 정보가 Redis에 저장된다. 따라서 Redis가 장애를 일으키면 결제 전 좌석 선택 기능도 영향을 받을 수 있다.

즉, v1의 주요 위험이 MySQL 락 경합이었다면, 개선 후에는 Redis 안정성이 중요한 운영 포인트가 된다.

특히 Redis를 단일 인스턴스로만 운영하면 다음 문제가 생길 수 있다.

- Redis 장애 시 임시 좌석 선점 기능 중단
- PendingBooking 조회 실패
- 결제 전 좌석 선택 요청 실패
- Redis에 저장된 임시 선점 데이터와 MySQL 확정 예약 데이터 사이의 검증 필요

따라서 운영 환경에서는 Redis를 단일 장애 지점으로 두지 않는 보완이 필요하다.

- Redis 장애 시 명확한 실패 응답 반환
- Redis Sentinel, Redis Cluster 또는 관리형 Redis 사용 검토
- Redis 응답 시간, 메모리 사용량, 명령 처리 지연 모니터링
- 만료된 임시 예약과 확정 예약 데이터 간 최종 검증 유지
- Redis 장애 상황을 가정한 복구 전략 수립

이번 개선은 MySQL 락 경합 문제를 줄인 대신, Redis의 가용성과 모니터링이 더 중요해지는 구조다. 따라서 포트폴리오에서는 성능 개선 수치뿐 아니라, Redis 장애 가능성과 이를 어떻게 보완할 것인지까지 함께 설명하는 것이 좋다.
